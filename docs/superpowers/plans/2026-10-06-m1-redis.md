# M1 — Sessions, Cache and Queue on Redis

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep the sessions, the cache, the rate limits and the queue in Redis. Run the
queue worker and the scheduler as separate services in the local stack.

**Architecture:** Compose adds three services: `redis`, `worker` and `scheduler`. The
`worker` and `scheduler` services use the same `dev` image and the same bind mount as
`app`. Only the command is different. The services share data only through PostgreSQL
and Redis.

**Tech Stack:** Docker Compose 2.32, Redis 8 (`redis:8-alpine`), phpredis (already in
the `base` image).

**Spec:** `docs/superpowers/specs/2026-09-28-event-booking-design.md` (sections 2 and
9), `docs/design/c4-containers.md`.

## Global Constraints

- The `.env.example` file sets `SESSION_DRIVER`, `CACHE_STORE` and `QUEUE_CONNECTION`
  to `redis`. The rate limits use the cache store, so they also use Redis.
- Failed jobs stay in PostgreSQL, in the `failed_jobs` table. Laravel cannot keep
  failed jobs in Redis.
- We keep all the default Laravel migrations, also `sessions`, `cache`, `cache_locks`,
  `jobs` and `job_batches`. These tables stay empty with the Redis drivers. Job batches
  (`Bus::batch()`) use the `job_batches` table with all queue drivers, so the table must
  stay for batches to work. The other tables let us go back to the `database` drivers
  with a change to `.env` only.
- The `worker` service runs `php artisan queue:listen --tries=1`. It loads the code
  again for each job, so code changes apply without a restart. Production (M2) uses
  `queue:work`.
- The `scheduler` service runs `php artisan schedule:work`. Only one scheduler runs.
- The tests keep the `array` and `sync` drivers from `phpunit.xml`. CI does not need a
  Redis service.
- `composer ci:check` runs inside the `app` container and must pass.

## Review Focus

1. **Sessions in Redis.** After a login, the session key is in Redis.
2. **The queue.** A queued email goes through Redis to the `worker` service and shows in
   Mailpit.
3. **The scheduler.** The `scheduler` service runs and logs its checks.
4. **Start order.** `app`, `worker` and `scheduler` start only when Redis and PostgreSQL
   are healthy.

### Task 1: Redis, worker and scheduler services

**Files:**

- Modify: `compose.yaml`
- Modify: `.env.example`

- [ ] **Step 1: Add the `redis` service and its volume to `compose.yaml`**

```yaml
redis:
    image: redis:8-alpine
    ports:
        - 6379:6379
    volumes:
        - redis:/data
    healthcheck:
        test: [CMD, redis-cli, ping]
        interval: 5s
        timeout: 3s
        retries: 20
```

Add `redis:` under `volumes:`.

- [ ] **Step 2: Move `depends_on` into the `x-app` anchor**

`app`, `worker` and `scheduler` all need PostgreSQL, Redis and Mailpit. The `vite`
service overrides `depends_on` with its own value (it waits for `app`).

```yaml
x-app: &app # build, image, volumes and extra_hosts do not change
    depends_on:
        postgres:
            condition: service_healthy
        redis:
            condition: service_healthy
        mailpit:
            condition: service_healthy
```

Remove the `depends_on` block from `app`.

- [ ] **Step 3: Add the `worker` and `scheduler` services**

```yaml
worker:
    <<: *app
    command: php artisan queue:listen --tries=1

scheduler:
    <<: *app
    command: php artisan schedule:work
```

These services have no ports and no health check.

- [ ] **Step 4: Change `.env.example`**

```dotenv
SESSION_DRIVER=redis
QUEUE_CONNECTION=redis
CACHE_STORE=redis
REDIS_HOST=redis
```

- [ ] **Step 5: Change the local `.env` in the same way, then restart the stack**

Run: `docker compose up -d --remove-orphans`
Expected: `docker compose ps` shows `app`, `vite`, `worker`, `scheduler`, `postgres`,
`redis` and `mailpit` as running. `postgres`, `redis`, `mailpit` and `app` are healthy.

- [ ] **Step 6: Commit**
